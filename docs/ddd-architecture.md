# 어그리게이트와 BC 경계

새 기능은 **업무 사실 → 소유 BC → 불변식과 생명주기 → 어그리게이트 → 트랜잭션·패키지** 순서로 설계한다. 클래스나 테이블을 먼저 나눈 뒤 그 구조를 업무 경계라고 설명하지 않는다. 아래 예제의 전제와 판단 기록을 먼저 읽고, 같은 전제에서는 같은 경계를 유지한다.

## 두 경계가 답하는 질문

| 경계 | 결정하는 것 | 판단 근거 |
| --- | --- | --- |
| BC, 바운디드 컨텍스트 | 어떤 업무 모델과 용어가 이 범위에서 같은 뜻으로 통하는가 | 업무 목적, 용어의 의미, 결정 책임, 변경 이유 |
| 어그리게이트 | 어떤 상태의 일관성을 한 루트가 함께 지켜야 하는가 | 불변식, 소유 관계, 독립적인 식별자·생명주기, 동시 변경 |

BC에는 여러 어그리게이트가 있을 수 있다. 어그리게이트에는 루트와 그 루트가 소유하는 엔티티·값 객체가 들어간다. 테이블 수, API 수, 같은 화면에 보이는지, 한 요청에서 함께 읽는지는 어느 경계도 단독으로 결정하지 않는다.

이 구분은 [Evans의 DDD Reference](https://www.domainlanguage.com/wp-content/uploads/2016/05/DDD_Reference_2015-03.pdf)의 Bounded Context·Aggregates와 [Fowler의 Bounded Context 설명](https://martinfowler.com/bliki/BoundedContext.html)을 따른다. 아래 업무 전제, 패키지 배치, 판단 절차는 이 템플릿의 선택이다.

## 현재 예제의 고정된 업무 전제

주문·재고 예제는 작은 상점의 **판매 접수 모델과 실물 보유량 모델**을 다룬다. 판매 담당은 판매 가능 품목과 주문·취소 정책을 정하고, 창고 담당은 실물의 등록·입고·보유량을 관리한다. 이 역할은 업무 책임을 뜻하며 실제 개발팀을 둘로 나누거나 서비스를 별도 배포하라는 뜻은 아니다.

판매 접수는 재고 유무에 의존하지 않는다. 선주문을 받을 수 있고 품절 대응은 예제 밖의 업무다. 판매품목과 재고품목은 각각 등록하므로 한쪽에만 SKU가 있을 수 있다. 두 BC 사이의 자동 동기화·예약·주문 이행은 요구사항에 포함하지 않는다.

| BC | 소유 모델과 결정 | 같은 단어의 의미 |
| --- | --- | --- |
| `ordering` | 판매 가능한 `Offer`, 고객이 접수한 `Order` | SKU는 판매품목의 업무 식별자, 수량은 주문자가 요청한 수량 |
| `inventory` | 실물 보유량을 가진 `StockItem` | SKU는 창고가 관리하는 품목 키, 수량은 실제 보유량 |
| `todo` | 개인 할 일의 제목과 완료 상태를 가진 `Todo` | 상점 모델과 독립된 간단한 할 일 관리 예제 |

**현재 주문·재고 분리는 이 전제에서는 유지한다.** 판매 가능 여부와 실물 보유량을 하나의 모델로 취급하면 서로 다른 결정을 혼동하기 때문이다. SKU 정규식, 별도 테이블, 별도 서비스가 있다는 사실은 분리 근거가 아니다. 실제 서비스에서 하나의 일관된 모델과 결정 책임으로 충분하다면 한 BC 안의 여러 어그리게이트로 시작할 수 있다. 개발팀이 하나라는 이유만으로 합치지도 않는다.

Todo도 명시적인 BC 목록에 등록한다. 단순 CRUD와 BC는 양자택일이 아니다. Todo의 구현은 계속 작은 CRUD이며, 등록은 할 일 모델의 소유 범위를 명확히 한다. 새 CRUD라는 이유만으로 매번 새 BC를 만들지는 않는다.

여기서 결정 책임은 사람 이름이나 팀 배치가 아니라 **그 업무 규칙과 용어를 정하는 권한**이다. 담당자가 바뀌어도 같은 모델과 규칙을 유지한다면 BC를 나눌 근거가 생기지 않는다. 반대로 같은 사람이 서로 다른 업무 책임을 맡아도 모델의 의미가 달라질 수 있다.

## 한 BC 안의 두 어그리게이트

```text
ordering BC
├── Offer 어그리게이트: 판매품목의 식별자·SKU·판매 상태
└── Order 어그리게이트: 주문 식별자·상태·접수 시각
    └── OrderLine 값 객체 1~10개: SKU·수량

inventory BC
└── StockItem 어그리게이트: SKU·보유량

todo BC
└── Todo 어그리게이트: 식별자·제목·완료 상태·생성 시각
```

### Offer와 Order를 나누는 이유

Offer는 주문이 없어도 등록하고 판매를 중단할 수 있으며 여러 주문에서 참조한다. Order는 고객의 요청으로 생성하고 취소하며, Offer의 판매 중단은 이미 접수한 Order를 변경하지 않는다. 두 모델은 같은 판매 접수 언어를 사용하지만 **독립된 생명주기와 상태 규칙**을 가지므로 같은 BC의 서로 다른 어그리게이트다.

Offer는 UUID인 `OfferId`를 API 식별자로, 유일한 `Sku`를 업무 키로 가진다. 상태는 `ON_SALE → DISCONTINUED`이며 반복 중단은 상태를 바꾸지 않는다. OrderLine은 Offer 객체를 보관하지 않고 SKU 값을 보관한다. 가격·상품 설명·재판매 기능은 구현하지 않는다.

### OrderLine을 Order 안에 두는 이유

Order는 **품목 1~10개, 주문 안에서 SKU 중복 금지, 품목별 수량 1~100**을 함께 지킨다. OrderLine은 주문 밖에서 독립적으로 생성·조회·저장하는 대상이 아니고, 접수 후 품목은 변경하지 않는다. 따라서 별도 루트나 저장소 없이 Order가 소유하는 불변 값 객체로 둔다.

`orders`와 `order_lines`는 **테이블 두 개로 저장하는 어그리게이트 하나**다. `OrderRepository`가 품목까지 함께 저장·복원한다. 부모 저장 후 품목 저장이 실패하면 전체를 롤백한다. 테이블을 추가했다고 어그리게이트가 늘어난 것은 아니다.

내부 항목을 개별적으로 식별하고 변경하는 업무가 생기면 루트 안의 자식 엔티티를 검토한다. 자식에게 ID가 생겼다는 사실만으로 독립 어그리게이트가 되지는 않는다.

### 불변식과 주문 시점의 정책

새 주문은 **Offer를 읽은 시점에 모든 SKU가 판매 중이어야 한다.** 그 조회 직후 판매 중단이 커밋되더라도 이미 읽은 판매 상태로 주문을 접수하는 것을 이 예제는 허용한다. 따라서 Offer 조회는 잠그지 않으며, 이후 Offer 상태와 기존 Order 상태가 계속 일치해야 한다는 불변식은 없다.

`OrderService`는 자기 BC의 OfferRepository를 읽고 OrderRepository만 쓴다. `OfferService`는 Offer만 바꾸며 Order를 수정하지 않는다. 한 유스케이스가 두 어그리게이트를 읽는다고 둘을 합치지 않는다.

요구사항이 '판매 중단 커밋 이후에는 진행 중 주문도 접수되면 안 된다'로 바뀌면 판정 시점, 잠금 순서, 실패·동시 실행 계약을 다시 정한다. 이를 단순한 검증 추가로 취급하거나 몰래 이벤트 전달로 바꾸지 않는다.

## 새 기능을 분류하는 절차

1. **요구를 명령·조회·업무 규칙으로 적는다.** 누가 무엇을 바꾸는지, 성공 후 상태, 허용하지 않는 상태, 동시 요청이나 중간 실패에서 지킬 것을 확인한다. 근거가 부족하면 불변식이 아니라고 단정하지 말고 필요한 업무 사실을 질문한다.
2. **기존 BC의 모델에 맞는지 먼저 확인한다.** 같은 용어의 의미와 결정 책임을 유지할 수 있으면 기존 BC에 둔다. 다른 업무 목적·모델을 독립적으로 유지해야 하는 구체적인 이유가 있으면 새 BC를 검토한다. 같은 단어의 충돌은 유용한 증거지만 필수조건은 아니다. 다른 BC가 데이터를 사용한다는 사실, 새 화면, 다른 담당자, 장래의 확장 가능성만으로 분리하지 않는다.
3. **조회에 필요한 사실이 이미 저장돼 있는지 확인한다.** 기존 조회로 충분하면 그대로 사용하고, 별도 응답 형태가 필요하면 해당 BC의 애플리케이션 모델과 조회용 Store를 사용한다. 같은 BC의 여러 어그리게이트를 합쳐 읽는 조회가 새 어그리게이트를 뜻하지 않는다. 취소 시각처럼 저장하지 않는 사실이 필요하면 그 사실의 소유 모델에 기록하는 변경도 별도로 설계한다. 예를 들어 월별 집계의 기준이 접수일인지 취소일인지 모르면 먼저 확인한다.
4. **변경할 상태가 기존 루트의 규칙·생명주기에 속하는지 확인한다.** 해당 루트를 통하지 않은 변경이 그 루트의 불변식을 깨거나, 상태가 루트와 함께만 존재한다면 필드·값 객체·자식 엔티티로 추가한다. 독립적으로 생성·변경·종료되고 자기 규칙을 지키는 대상이면 같은 BC의 새 어그리게이트를 검토한다. 조회 편의를 위해 전체 객체 그래프를 한 루트에 넣지 않는다. 무제한 이력·큰 컬렉션·불필요한 잠금 경합이 생기면 소유와 보존 요구부터 재검토한다.
5. **트랜잭션과 실패 계약을 별도로 적는다.** 예제의 기본은 다른 어그리게이트를 읽고 하나를 변경하는 방식이다. 여러 루트의 쓰기가 꼭 원자적이어야 한다면 불변식과 경계를 재검토하고, 필요한 이유·잠금·롤백·실패 계약을 기록한다. 같은 트랜잭션으로 묶고 싶다는 이유만으로 루트나 BC를 합치지 않는다. 연동이 필요하다는 이유만으로 비동기 전달을 추가하지도 않는다.
6. **결정한 모델을 코드와 검사에 반영한다.** 아래 배치 규약, 루트별 저장소, 실제 커밋·롤백 테스트를 따르고 BC·루트 목록을 함께 갱신한다. 경계 선정 이유를 바꾸는 요구라면 기존 결정을 조용히 덮어쓰지 말고 변경 이유를 기록한다.

### 변경 설명에 남길 최소 기록

기존 루트의 단순 필드·규칙 변경은 소유 루트와 검증할 규칙을 한 문장으로 남긴다. **새 BC·어그리게이트, 생명주기·일관성·연동 계약 변경**에는 다음을 변경 설명이나 관련 문서에 적는다.

```text
요구와 확정된 업무 사실:
소유 BC와 선택 근거:
루트·소유 상태·불변식·독립 생명주기:
유스케이스가 읽는 것 / 쓰는 것 / 판정 시점·실패 계약:
분류 결과와 채택하지 않은 대안의 이유:
변경할 패키지·경계 목록·행동 테스트:
불명확한 사실과 필요한 질문:
```

이미 주어진 요구로 판단할 수 있는 부분은 이 기록을 작성하고 구현한다. 모든 변경에 별도 승인을 요구하는 절차가 아니다. 결과를 바꾸는 업무 사실이 빠졌을 때 질문하며, 빈칸을 임의의 사업 규칙으로 채우지 않는다.

기존 BC 어디에도 맞지 않는데 새 업무 목적·모델도 불명확하면 배치를 보류하고 필요한 사실을 확인한다. Todo나 공용 도메인을 미분류 기능의 임시 집합으로 쓰지 않는다. 별도 업무 모델이 확인된 CRUD는 새 BC로 등록할 수 있고, 기존 모델의 CRUD 확장은 그 BC에 둔다. 업무 모델이 없는 기술 설정·연결 기능은 해당 `config`·어댑터에서 구현하며 BC를 신설하지 않는다.

BC를 정할 수 있어도 어그리게이트의 소유·생명주기가 미정이면 루트와 테이블은 확정하지 않는다. 예를 들어 점검 업무에 장비 식별자가 등장해도, 이 시스템이 장비 자체를 생성·관리하는지 모르면 Equipment 루트를 자동으로 만들지 않는다. 분명한 판단과 미정인 판단을 기록에서 구분한다.

## 분류 사례

**주문 접수 후 수량을 바꾸되 주문별 SKU 중복 금지·수량 범위·취소 후 변경 금지를 지킨다.** 기존 Order의 변경이다. 루트를 잠그고 루트의 메서드로 품목 값을 교체한다. OrderLine 저장소나 새 BC를 만들지 않는다.

**판매 중단한 품목을 다시 판매할 수 있게 한다.** 기존 Offer의 상태 전이 변경이다. SKU·판매 상태의 의미와 책임은 같으므로 새 Offer나 BC를 만드는 이유가 없다. 현재의 종료 상태 규칙과 테스트를 명시적으로 바꾼다.

**판매 상담원이 주문별 반품 요청을 접수·심사하며, 요청마다 독립 식별자와 상태가 있고 승인해도 원래 주문 상태는 바꾸지 않는다.** 현재 판매 접수 모델의 언어와 책임을 유지한다는 전제에서 `ordering`의 새 ReturnRequest 어그리게이트로 둔다. OrderId로 참조한다. 반품 가능 총수량처럼 여러 요청·주문에 걸친 제약이 추가되면 이 전제와 원자성 계약을 다시 검토한다.

**구매 담당자가 공급자에게 발주하고 납기·공급자 조건을 관리하며, 판매 주문과 독립적으로 변경하고 창고 입고는 수동으로 처리한다.** 구매 발주는 고객 주문과 다른 업무 모델이므로 `purchasing` 같은 새 BC로 분류한다. 독립적인 업무 목적과 결정 책임이 명시된 사례이며, 단지 Order 클래스가 하나 더 필요해서 나누는 것이 아니다.

**판매 중인 품목별로 접수된 주문 수량을 보여준다.** `ordering`의 조회 모델이다. Offer·Order를 함께 조회해도 두 어그리게이트는 유지한다. 실물 보유량까지 필요하면 아래 BC 간 연동 계약이 추가로 필요하다.

**상품 정보를 추가한다.** 이것만으로 Catalog BC를 결정하지 않는다. 판매품목에 표시할 짧은 설명인지, 별도 담당자가 여러 판매 채널에 배포하는 상품 원장을 관리하는지부터 확인한다. 명사가 같아도 확정된 요구에 따라 기존 Offer의 필드 또는 다른 모델이 될 수 있다.

## 코드 배치와 소유권

```text
<bc>/domain/                         그 BC에서 의미가 같은 공유 값·예외
<bc>/domain/<aggregate>/             루트 하나와 소유 ID·값·엔티티
<bc>/domain/<aggregate>/<helper>/    같은 어그리게이트의 내부 구성
<bc>/application/port/input/         BC의 유스케이스 계약
<bc>/application/port/output/        루트별 Repository, 필요한 조회 Store
<bc>/application/service/            같은 BC의 유스케이스 구현
<bc>/adapter/inbound/web/            HTTP 계약
<bc>/adapter/outbound/persistence/   해당 BC가 소유하는 저장소·테이블
config/                             빈 조립
```

이 템플릿에서는 **계층 앞의 업무 패키지 하나가 BC 하나**다. `ordering.orders.domain`처럼 BC 아래에 다른 기능 경로를 만들지 않고 `ordering.domain.order`에 어그리게이트를 둔다. 일반 아키텍처 검사기는 더 많은 패키지 형태를 지원하지만 운영 코드의 BC·루트 목록 검사는 이 배치로 제한한다.

다른 어그리게이트의 루트를 도메인 필드로 보관하지 않는다. 같은 BC 안에서는 의미가 맞는 ID·불변 값을 참조할 수 있고, 애플리케이션 서비스가 각 저장소를 통해 루트를 다룬다. 같은 BC의 값이라고 무조건 공유하지 않으며, 의미와 제약이 같은 경우에만 BC의 `domain`으로 올린다.

루트 공용 `domain`에는 기술 표식인 `AggregateRoot`만 둔다. 두 BC의 Sku나 업무 모델을 공용 패키지로 옮겨 경계를 없애지 않는다. BC 간에는 상대 도메인·애플리케이션 타입과 테이블을 직접 사용하지 않는다.

### BC 간 연동 요구가 생기면

현재 예제는 BC 사이에 데이터를 전달하지 않는다. 연동 요청은 공개 데이터 계약, 모델 번역, 변경 책임, 판정 시점, 실패·재시도·원자성 요구와 필요한 검사 변경을 함께 설계한다. 공용 포트나 함수 값을 `config`에서 연결해 현재 금지된 업무 결합을 숨기지 않는다. 같은 DB나 같은 JVM이라는 이유로 다른 BC의 테이블을 직접 읽고 쓰지 않는다. 전달 기술은 요구가 정해진 뒤 선택한다.

연동을 추가할 때도 각 BC의 유스케이스가 자기 변경과 트랜잭션을 소유하는 것을 기본으로 한다. 여러 BC의 쓰기가 한 번에 커밋돼야 한다면 기존 분리 전제와 원자성 요구를 함께 재검토한다. 트랜잭션 하나가 필요하다는 사실만으로 BC를 자동 병합하거나, 실패를 무시하고 두 호출을 이어 붙이지 않는다.

소비측 코어는 자기 모델과 출력 포트를 사용하고 외부 공개 데이터와의 번역은 어댑터에서 맡는다. 구체적인 호출 방식과 어댑터 경로는 요구사항으로 정하며, 현재의 계층·포트 검사에서 허용하는지 확인한다. 특히 인프로세스 어댑터가 상대 입력 포트를 직접 호출하는 형태는 현재 일반 검사에도 걸리므로 해당 연동 계약과 정상·위반 fixture를 함께 설계해야 한다. 이 문서는 아직 선택하지 않은 전달 구현을 기본 제공한다고 가정하지 않는다.

## 자동 검사와 완료 조건

`HexagonalArchitectureTest.contextAggregates`가 운영 BC와 루트의 명시적인 목록이다. 현재 `todo → todo.Todo`, `ordering → order.Order, offer.Offer`, `inventory → stock.StockItem`을 선언한다. 새 업무 패키지와 새 표식 루트가 이 목록과 다르거나 선언한 BC가 코드에 없으면 실패한다.

공통 헥사고날 검사 24개, DDD 검사 9개, BC 검사 2개와 목록 검사를 함께 실행한다. 결합된 정상·위반 fixture로 같은 BC의 ID 참조·여러 저장소 사용·루트 내부 하위 패키지는 허용하고, 다른 어그리게이트 루트 참조·다른 BC 코어 의존·잘못된 루트 위치는 거부함을 확인한다. 상세 기술 규약은 [코드 품질 규칙](code-quality.md#어그리게이트와-ddd-경계)을 따른다.

정적 검사는 선언한 경계와 직접적인 바이트코드 의존을 검증한다. 업무 의미, 루트 표식을 누락한 새 모델, 함수 값·반사·인라인·값 클래스 소거를 거친 모든 결합을 증명하지는 않는다. **경계 선정은 업무 사실과 판단 기록으로 검토하고, 구현한 불변식·실패 경로는 행동 테스트로 검증한다.** 기준을 고정해도 요구사항에 없는 사업 결정을 자동으로 맞힐 수는 없다.
